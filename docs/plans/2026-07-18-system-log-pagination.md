# 系统日志服务端分页实施计划

**状态：** 已完成
**目标：** 把系统日志从固定加载 200 条升级为可验证的服务端分页，降低响应体和 DOM 数量，并修正过滤总数不准确的问题。

## 当前问题

- `/api/logs` 先过滤再截断，但 `filtered` 返回的是截断后的数量，不是真实过滤总数。
- 前端固定请求 200 条并一次性渲染，日志增长后加载、筛选和展开成本持续增加。
- 历史页如果继续自动刷新，新日志插入会让相同偏移量对应的内容漂移。
- 现有“导出日志”实际只导出当前已加载条目，界面没有说明范围。

## 响应契约

`GET /api/logs?date=YYYY-MM-DD&limit=50&offset=0` 返回：

```json
{
  "date": "2026-07-18",
  "total": 420,
  "filtered": 128,
  "returned": 50,
  "offset": 0,
  "limit": 50,
  "page": 1,
  "pageCount": 3,
  "hasPrevious": false,
  "hasNext": true,
  "entries": []
}
```

其中 `total` 是原始可解析日志数，`filtered` 是应用级别和模块条件后的完整数量，`returned` 才是当前页返回数量。

## 非目标

- 本轮不改变日志保留天数和文件轮转。
- 本轮不把文件日志迁移到 PostgreSQL。
- 本轮仍需扫描指定日期文件才能完成任意模块筛选；分页主要减少网络响应和前端 DOM，文件索引属于后续存储优化。
- 日志内容不得包含认证密钥、WxPusher 凭据或真实券商材料。

# 0025：同机SQLite旁路保存Paper长期复盘证据

- 状态：接受；实现与发布验证见本轮计划。
- 日期：2026-11-09。
- 被取代关系：不取代JSON交易账本；PostgreSQL交易存储仍为未来设计。

## 背景

用户授权在同一4核、约3.7GiB服务器增设数据库与后台能力。当前订单/审计只保留7天，难以判断长期无交易原因与真实Paper表现；独立数据库也不能解决错误策略或上游延迟。服务器磁盘约剩12GiB，优先选择Python标准库SQLite，避免为单实例归档增加常驻数据库和连接池。

## 决策

新增`paper_history.py`，systemd每分钟低优先级启动，无网络、只有归档目录可写。只观察原子替换的JSON账本，不调用Broker或外部行情。保留订单365天、账户5分钟成本/现金样本和白名单自动执行摘要90天；开放订单不按年龄删除。库页容量最多256MiB，WAL和3份每日在线备份另占空间；达到上限失败，不扩容至填满磁盘、不删除交易状态。

JSON version1兼容增加`accountEpoch`，旧账本首次加载时持久生成UUID，重启/暂停/配置变化保持，重置才改变。归档的账户世代、订单、运行主键复合隔离；旧账本升级沿用原有历史清理规则，不恢复已清理记录。无效显式世代失败，不能重新猜测归属。

全量输入校验后事务提交；重复轮询幂等、同一挂单成交更新同一行、过期源不会把终态回退为挂单。只保留指定订单数值、策略键、现金/成本和固定运行枚举/计数/来源问题代码，不保存任意审计data、供应商原始错误、凭据、新闻正文或原始行情响应。

## 结果与代价

归档与撮合失败隔离，数据库损坏/满额只导致归档失败；任务资源上限为单核25%CPU、192MiB内存、45秒，撮合不等待归档完成。交易主账本、实时行情和账户权益计算仍由原系统负责，归档样本没有市值价格，不可据成本样本伪造实时净值。

这是轮询观察副本，不能保证捕获两次采样间被重置删除的记录，也不能恢复首次安装前丢失的历史。备份同盘，仅用于逻辑损坏恢复，不能抵御服务器/磁盘丢失。多账户/高并发交易事务未来仍需独立迁移、对账与恢复方案；本模块没有多实例执行或真实交易权限。

# 0047：多市场Paper采用独立资金与显式主账本迁移

- 日期：2026-11-10（北京时间）。
- 状态：接受目标设计；多账户事务主账本和期货撮合尚未实现或激活。
- 被取代关系：不替代当前JSON主账本或[0025只读SQLite归档](0025-read-only-sqlite-paper-history.md)；将未来存储方向细化为单机事务优先、多实例再评估PostgreSQL。

## 背景

用户要求股票、期货拥有各自资金并行Paper交易，并允许增强同一服务器。当前Store/System只有PAPER-CN-01，订单与持仓没有账户/市场键，期货只有连续主连研究数据。直接多开当前Store、共享JSON或将主连放进股票Broker会混淆资金、规则与交易日。

## 决定

以[多市场Paper账本目标设计](../architecture/multi-market-paper-ledger.md)作为唯一详细设计：

1. 原20000元A股账户/世代/历史保持；期货本金另配，不自动划走股票现金。账户/世代/市场/币种贯穿资金、订单、风险与幂等，主连与具体合约分开。
2. 当前单机后续优先验证单writer事务SQLite。先锁定并验证Windows/Node20-alpine兼容驱动或独立运行时升级；通过前不配置新主账本，不把现有归档库当成交易账本。
3. 迁移使用离线预检、可信备份、静止源导入、两端只读对账和唯一writer栅栏后原子激活。禁止交易双写；有新写入后不能恢复旧JSON丢掉新交易，只能兼容前向修复或完整核对的反向迁移。
4. 期货必须具备具体合约合格报价、版本化乘数/tick/费用/保证金、专用开平仓/多空、夜盘交易日、结算与故障恢复后才启用；取消股票固定比例现金预留不取消期货保证金。
5. 共享行情和研究不扩展订单权限；单账户失败不能直接关闭其他市场，宿主总资源预算仍有界。增加后台能力以有效吞吐/延迟和一致性验证，不以资源满载作为完成标准。

## 结果与代价

设计先固定迁移和资金隔离验收，后续分模块实现存储适配器、迁移工具、账户路由、具体期货报价/规则、撮合/保证金、结算/恢复与策略回放。不会在缺少合约规则和结算的情况下宣称已开启期货交易，也不承诺成交数量、胜率或收益。详细故障矩阵与当前事实只保留在权威设计，避免多文档复制后漂移。

# 0032：留存上一健康发布的源码和镜像材料

- 状态：接受，隔离验证通过；首次安装与随后生效须分开核验。
- 日期：2026-11-10（北京时间）。
- 被取代关系：替代0026成功后不留持久恢复材料的限制；保留已有发布中回退、镜像复用和代理刷新，不迁移交易账本。

## 背景

频繁发布后，临时rollback镜像标签和源码备份立即删除。服务器没有Git工作区，只有外部核验记录；宿主全局dangling-image prune不能证明资源归属。先保留可核验的上一份材料，才能设计后续应用范围内清理。

## 决策

`deploy/release_retention.py`在现有发布锁下运行。替换源码前，将当前源码打包至受限`runtime/releases/release-<随机16hex>`，仅保留源码文件，排除runtime、Git、私有.env路径和Python缓存；源码符号链接拒绝，最多10000文件/128MiB。三服务当前production标签必须等于实际healthy容器镜像，随后对确切镜像ID建立本槽位专属retained标签。manifest保存归档SHA256、源码清单摘要、镜像ID和0026运行指纹。

新版本三服务及HTTP健康通过后，重新验证全部留存材料，再原子替换index中的previous指针和本次current身份。发布失败不改旧指针，本次尝试退出时只清自身槽位/标签。正常替换完成后只清原previous的确切专属标签和两项文件，不进行宿主全局prune。旧槽清理失败只记录警告，不能把已健康且已提交的发布伪装成失败；异常中断留下的槽位保留待复核，四个槽位后阻止新建，避免无界增长。

源码身份以保存过的current清单摘要和镜像集合为依据；相同提交且内容/镜像一致的重复发布保持原previous。首次启用或手动改动导致无法匹配时，上一提交标识为null，不能把猜测的SHA写成事实；实际源码归档和镜像仍可核验。外部`production-release.json`不作为未经源码比对的身份兜底。Python缓存不参与清单，运行verify本身不会改变身份。

留存工具与指纹模块先复制至本次私有临时目录，源码更新或目标旧版本缺少工具时，整次发布仍使用同一实现。首次安装仍由旧发布器执行，只能宣称工具上线；下一次发布才实际生成留存材料。

`verify`只读检查previous材料并报告current记录，`export`在核验后以不覆盖方式导出源码。它们不会恢复/清空账户，也不自动停止容器或执行回滚。恢复运行需另外核对持久账本格式、配置与镜像兼容性，并走明确发布/恢复流程。本模块没有免构建的一键恢复命令。

## 结果与代价

健康发布保留一份上一源码及三个镜像引用，正常轮换只留一槽，异常场景最多四槽后要求处理；镜像共享层不重复按标称大小估算磁盘。保留旧镜像会占用必要空间，不能将它当作可回收缓存。归档、哈希和Docker读取增加少量部署工作，不新增常驻服务。

同盘材料不包含账户、密钥、证书或灾难恢复能力。生产仅正常发布和只读核验，不主动失败演练。验证见[执行计划](../plans/2026-11-10-server-release-retention.md)，Linux真实shell/私有目录/Docker替身覆盖失败、重复、槽位切换和完整性。

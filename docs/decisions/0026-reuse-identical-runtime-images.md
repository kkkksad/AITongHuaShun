# 0026：发布时复用相同运行内容的已验证镜像

- 状态：接受；线上复核见本轮计划。
- 日期：2026-11-09。
- 被取代关系：不取代Compose配置/健康校验，不改变交易权限。

## 背景

连续发布的AkShare桥接平台manifest和config摘要相同，OCI构建证明和manifest-list摘要变化，使Compose反复重建容器。每次重启都会清空内存行情/研究缓存，重新预热可能暂时降低交易输入覆盖。

## 决策

保留完整构建及证明生成。构建后，对上一已验证镜像与新镜像比较`Config`、`RootFS`、`Os`、`Architecture`、`Variant`、`OsVersion`、`OsFeatures`的规范JSON哈希；仅忽略这些字段之外的顶层构建/引用元数据。环境、入口、健康检查、用户、标签、程序层、平台或层顺序变化都会改变指纹。

指纹相同则把production标签指回上一已验证镜像，连同原构建证明复用；指纹不同则正常发布新镜像。Compose继续比较服务环境、挂载和配置，全部服务仍须通过健康检查。无法计算合法指纹时回退，不把失败视为相同。已知旧归档没有该工具时沿用旧版标准发布，保持旧版本回部署能力。

构建、指纹、启动或健康失败时，先恢复旧源码和Compose，再用旧镜像启动；源码/配置与镜像必须属于同一次发布。Linux临时沙箱使用真实shell脚本、Docker替身和独立目录复现，不以中断生产验证错误分支。

保留web时还须检查代理依赖：Nginx在启动时解析静态上游名，后端容器更新可能改变地址；单文件bind在源码替换后也可能继续引用旧配置inode。启动前记录后端/web容器ID并比较期望配置与容器内配置哈希；正常Compose启动后，若web未变且后端已变或配置不一致，仅强制重建web。无关发布保持三容器；读取期望配置失败或代理刷新失败沿用整套恢复路径，不刷新行情容器。

## 结果与代价

程序与配置未变的服务可保持容器、连接和内存缓存。仍会执行构建，且不会把新的证明附会到旧运行镜像。首次发布安装新部署脚本；该次正在运行的仍是旧部署器，需下一次发布验证复用行为。

当前成功后仍清理临时rollback标签和源码备份；这是部署过程恢复，持久上一发布资源另行设计。相同运行内容不能证明策略有效、接口数据新鲜或服务有资格交易，所有原有交易检查保持。

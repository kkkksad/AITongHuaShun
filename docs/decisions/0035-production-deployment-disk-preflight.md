# 0035：发布前分别检查应用与Docker存储可用空间

- 状态：接受，隔离验证通过待部署。
- 日期：2026-11-10（北京时间）。

## 背景

单机4核/3723MiB，休市采样CPU和内存尚有余量；多次构建后磁盘可用空间下降至约6.5GiB。Docker镜像与BuildKit缓存共享底层数据，不能相加解释可释放空间。无标签镜像也可能是OCI索引引用的运行内容，因此不因dangling状态全局清理。

## 决策

发布器持有既有部署锁、确认环境后，先调用当前安装的`deploy/deployment_capacity.py`；在归档解压、源码备份/替换、镜像构建和容器变化之前，检查应用路径和`docker info`返回的实际DockerRootDir均可访问且各自至少4GiB可用。Docker信息读取15秒超时，缺路径/权限/异常明确失败；不得退回假定Docker使用应用分区。同一文件系统的两次读数不求和。

阈值是操作下限，不是构建峰值保证；部署锁也不能阻止其他应用消耗磁盘。检查失败不自动删镜像、缓存或账户数据，当前源码与服务保持。正常stdout是可核验JSON，失败返回75；安装工具为空或符号链接返回78，不能降级为旧路径。工具输出包含两个非敏感路径和字节数，不包括环境或凭据。

首次安装仍使用旧发布器，因此发布前先从私有临时副本运行同一只读检查，并在安装后再次核验。后续新发布自动使用当前安装工具；目标归档较旧、没有该工具时，本轮检查仍执行，若回到真正旧发布器其后不自动具备此功能。完全未安装工具的旧系统保留显式legacy路径，不能声称已检查容量。

不增加后台进程，不修改CPU/内存限额，不把休市低负载当成盘中容量结论。不删除未知构建缓存；可回收策略须另行验证归属和当前/上一/在途保护。

## 验证

9项单元测试覆盖精确4GiB、少1字节、Docker与应用分区任一不足、同盘不能相加、读取异常、路径无效和只读命令超时设置；首次运行因新模块不存在导入失败，不计业务复现。实际发布shell新增5项验证容量失败/损坏工具不触碰源码/容器，以及旧目标兼容；旧发布器在这些案例应失败，新发布器通过。完整Linux套件60项包含原46项、9项单元和5项shell，Bash语法和4项发布静态契约通过。
